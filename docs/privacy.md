# Privacy and trust

The signaling server sees the IP address, request origin, user agent, temporary device ID, friendly name and signaling metadata, including SDP and ICE candidates; its hosting provider or reverse proxy may log network requests. It does not store or process file contents. Friendly names are random, not identity verification. Device type is derived from the browser user agent and can be incorrect.

File names, sizes, media types and content are sent over the WebRTC data channel. The recipient is asked to approve before chunks are accepted. WebRTC encrypts transport, but this implementation does not independently authenticate signaling end-to-end; a malicious signaling operator could interfere with peer establishment. A TURN relay, if used, observes connection metadata and relays encrypted traffic. Operator, infrastructure and relay policies must be published for the real deployment.

No analytics or ads are included. Verified received files are retained in browser private storage (OPFS where supported, otherwise IndexedDB Blob segments) until removed, site data is cleared, or the browser evicts it. When the receiver selects a destination folder, files are saved there instead; removing the history entry does not delete that copy. Downloads may create additional copies. An interrupted transfer may leave temporary private storage data. Clearing site data does not delete files saved elsewhere. Presence exists only while connected in server memory; the operator must separately define proxy log retention. Local subnet discovery can expose your device name and type to other users on a matching network; shared public-IP discovery can group unrelated users behind the same NAT.
